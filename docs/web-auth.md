# Local users and shared web sessions

## Contract

The framework uses unmodified **Tinyauth 5.2.0** behind Caddy's native
`forward_auth`. Human users log in once on `auth.<project>-<port>.localhost`;
the panel, Dagu, OMB and explicitly authorized applications share that session.
There is no browser HTTP Basic challenge. Unknown applications and users without
an explicit application allowlist entry are denied.

The login service is project-local, including its SQLite session database,
ports, cookie domain and runtime files. Different projects do not share identities
or sessions automatically. The domain includes the port block because browser
cookies are not isolated by port. Historical `panel.localhost`, `dagu.localhost`
and `omb.localhost` links redirect to the canonical project domain.

This implementation supports **local loopback HTTP only**. Startup rejects a
non-loopback `FYSO_BIND`. Remote HTTPS, Secure cookies, domain/certificate ownership
and trusted remote proxies require Phase 6 acceptance before exposing it remotely.
Do not bypass that gate by editing the generated runtime file.

## Configurable domain and shared login (D61)

Both settings are Copier answers (`.copier-answers.yml`, changed with `copier update`).
Empty answers give the contract above, unchanged.
The bare value `localhost` is reserved for legacy redirects and is rejected;
leave the answer empty for the local default or choose a project-specific domain.

| Answer | Variable | Empty (default) | Set |
|---|---|---|---|
| `web_domain` | `FYSO_WEB_DOMAIN` | `<slug>-<port>.localhost` | Any DNS name that resolves to this host on a private network. Applications live at `panel.<domain>`, `dagu.<domain>`, … on the project's HTTP port |
| `auth_upstream` | `FYSO_AUTH_UPSTREAM` | The project runs its own Tinyauth on `FYSO_AUTH_PORT` | `127.0.0.1:<port>` of a login service shared by several projects on this host |

**Shared login.** The gateway asks the shared service instead of its own. The project
starts no Tinyauth (its `web-auth` process idles so the stack keeps one shape), `setup`
creates no web users, `web-auth:users` refuses to run, and `project/auth/tinyauth.yaml`
is not read: users and application permissions belong to the shared service. That
service must be a Tinyauth whose cookie domain is a parent of every project's
`web_domain`, with an application entry (`apps.<name>.config.domain`) for each address
it protects. Signing out of one project signs out of all of them.

**Still loopback, still HTTP.** Neither answer changes `FYSO_BIND`. A domain other than
`*.localhost` is reached through a private forwarder that delivers to loopback, such as
an SSH tunnel or `tailscale serve --tcp <port> tcp://127.0.0.1:<port>`. The session
cookie is not `Secure`; use this only inside a private network. HTTPS comes from a
provider extension (next section); a public server with its own domain remains behind
the Phase 6 gate.

The shared login service and a portal in front of it are not generated by the template.

## HTTPS through a provider extension (D62)

The core issues no certificates. An extension that already terminates TLS for the
project's network (a NetBird reverse proxy, Tailscale) fronts the loopback gateway and
declares the public scheme in its mise conf.d file:

```toml
[env]
FYSO_WEB_SCHEME = "https"
```

| | No provider (default) | `FYSO_WEB_SCHEME=https` |
|---|---|---|
| Gateway | loopback, HTTP, `FYSO_HTTP_PORT` | the same |
| Address people use | `http://<app>.<web_domain>:<port>` | `https://<app>.<web_domain>` |
| Login redirects (`appUrl`, `X-Forwarded-Proto`) | `http` | `https` |
| Session cookie | not `Secure` | `Secure` |
| Accepted `Origin` | the `http` address with its port | the `https` address only |
| Panel links, OMB public address, start message | `http` | `https` |

The provider must deliver each `<app>.<web_domain>` name to the gateway port with the
original `Host` header, and `web_domain` must be a domain it serves. App links declared
on the listening address (`http://<app>.<web_domain>:<port>`) are rewritten in the panel
data; extension routes keep their `http://…:{$FYSO_HTTP_PORT}` site addresses, which is
where the gateway listens. One helper holds the rule: `web_origin <app>` in `lib.sh` and
`framework/scripts/web-origin.cjs`. Launchers read the value fresh from mise, so a
provider installed while the stack runs applies on the next restart of the gateway and
the login.

Who can open the provider's address (anyone, peers only, groups) is configured in the
provider, not here: the project's login and application permissions still apply to
every request.

Verified (2026-11-11): real Caddy 2.11.9 and Tinyauth 5.2.0 run the whole gateway suite
in both modes (`tests/test_web_auth_http.py`, 25 tests); in HTTPS mode the login
redirects to `https://auth.<domain>/`, the cookie is `Secure` and the listening address
is rejected as an origin. A real project (framework `v0.1.0-rc.3`, `fyso-ext-netbird`
`v0.4.0`, self-hosted NetBird reverse proxy) serves its panel, login, Dagu, OpenMausBot
and two project apps on `https://<app>.<host>.<cluster domain>` with trusted
certificates; a browser request to the panel is redirected to `https://auth.…/login`
with an `https` return address, and `mise run doctor` passes. Not verified: a person
signing in with a browser through the provider, and the bundled SilverBullet extension
behind HTTPS.

## User-visible flow

1. Open the panel. Caddy redirects a browser without a session to the native login
   screen. API and configuration requests receive 401/403 rather than login HTML.
2. Enter a local username and password. Tinyauth owns password verification,
   retry protection and the opaque HttpOnly, SameSite=Lax cookie.
3. Navigate between authorized applications without another login. The panel
   displays the authenticated identity and offers **Sign out** (ES/EN).
4. Sign out from the panel. The native authority deletes the server-side session;
   replaying the previous cookie fails on every site. Open native application tabs
   can retain rendered content, but subsequent requests require authentication.
   Existing long-lived upstream connections are not forcibly terminated by this
   gateway session change; reconnects require authentication. Immediate stream
   revocation is not part of the verified contract.
5. The panel checks its identity on focus and periodically. A changed identity
   reloads the page instead of retaining the previous user's in-memory state.

New projects use a 30-day session expiry and maximum lifetime (2592000 seconds)
in the native configuration. Sign out and credential changes still invalidate sessions.
Existing projects keep their project-owned settings; to adopt these defaults, set
`auth.sessionExpiry` and `auth.sessionMaxLifetime` to `2592000` in
`project/auth/tinyauth.yaml` and restart the project. Five failed attempts lock an
account for five minutes.
TOTP is available natively but is not automatically provisioned or required.

## Configuration and ownership

| File / variable | Owner and purpose |
|---|---|
| `project/auth/tinyauth.yaml` | Project-owned native configuration: application ACLs, lifetime, future OAuth/LDAP configuration |
| `secrets.enc.yaml` → `FYSO_AUTH_USERS` | SOPS-encrypted native `username:bcrypt` entries, comma-separated; optional native TOTP suffix |
| `FYSO_ADMIN_PASSWORD` | Legacy variable name for Dagu's technical credential; newly generated projects use a random value |
| `FYSO_AUTH_PORT` | Last port of the core block, `port_base+9`; listener binds to loopback |
| `FYSO_AUTH_UPSTREAM` | Empty, or the shared login the gateway trusts instead of the project's own (D61) |
| `.data/web-auth/runtime/` | Private, ignored generated config, session database and native runtime state |
| `.data/web-auth/bin/` | Rebuildable native binary; no machine-global auth service |

`mise run setup` creates the first human login with a hidden password prompt
(12–72 bytes; spaces are allowed, so a memorable passphrase works), or the
installer's private `FYSO_INITIAL_PASSWORD_FILE`. An empty answer, or no terminal
(SSH, a script), generates a readable password of four short groups
(`kfmt-pwze-rqsu-7dnx`, about 79 bits) and prints it. It never
falls back to `admin/admin`. Initial human passwords and Dagu's new random
technical password are separate. Existing projects retain their technical
credential until it is explicitly rotated.

**Extension apps (D58).** An installed extension's site
(`http://<app>.{$FYSO_WEB_DOMAIN}` in `extensions/*/Caddyfile`) gets a copy of
the `panel` rule in the runtime configuration, unless `apps.<app>` is declared
in `project/auth/tinyauth.yaml`. Panel users can already install and run
extensions, so this grants nothing new; declare the app to restrict it. Apps of
`project/apps/` stay explicit.

Manage local users and their passwords (D64):

```sh
mise run web-auth:password                  # show the administrator's password
mise run web-auth:password -- alice         # show another user's
mise run web-auth:password -- --new         # set a new generated one and show it
mise run web-auth:users add alice           # typed twice, or empty to generate
mise run web-auth:users remove alice
```

The login service only receives bcrypt hashes (`FYSO_AUTH_USERS`). Each password is
also kept, encrypted, in `secrets.enc.yaml` (`FYSO_AUTH_PASSWORDS`, a JSON map) so it
can be read again: whoever can decrypt that file can already replace a hash and sign
in, so this adds no access. Passwords are printed only by these terminal tasks (they
are `raw`, because mise redacts secrets in task output); the panel never shows them.
A user created before D64, or by an installer that sends only the hash, has no stored
password: `web-auth:password` says so and `--new` fixes it.

The stack may keep running: the login service alone is stopped and started around
the change, and it reads the users fresh from the encrypted file.

Verified (2026-11-11) on a real running project behind an HTTPS provider:
`web-auth:password` reported the pre-D64 administrator as not stored, `-- --new` set a
generated password with the stack up, and signing in with it through
`https://auth.<web_domain>` answered 200 with a `Secure` cookie on the project's own
domain (401 with a wrong password).

`add` also changes an existing user's password. Changes preserve unrelated
encrypted secrets and invalidate **all** existing web sessions. The bootstrap
administrator and last local account cannot be removed through this helper.
Permissions are explicit and separate from account creation. Native Tinyauth
`users.allow` is a comma-separated **string**, for example:

```yaml
auth:
  acls:
    policy: deny
apps:
  panel:
    users:
      allow: "admin,alice"
  omb:
    users:
      allow: "admin"
```

Grant panel or Dagu access only to trusted project operators. Those applications
can execute privileged project workflows; the gateway does not turn them into
read-only or tenant-isolated applications.

## Existing-project migration

Stop the project before updating the template and initializing local users. New
project-owned auth files are created once; later Copier updates preserve them.
Existing project/extension Caddyfiles and app links must move from `*.localhost`
to the canonical `*.<slug>-<port>.localhost` domain, and receive explicit native
ACLs. Those project-owned routes are not overwritten automatically. Only the
three built-in historical URLs have redirects. Back up the encrypted secrets and
age key before migration; the old shared password is not imported as a human user.

## Future identity providers

Applications depend only on the existing `fyso_login` snippet and trusted
`Remote-User`, `Remote-Name`, `Remote-Email` and `Remote-Groups` headers. Caddy
removes browser-supplied identity headers and Authorization before consulting
the authority. It strips the shared web-session cookie before proxying to an
application. The only cookie-retention exception matches both the canonical panel
host and its authority-backed `/api/session` or `/api/session/logout` handler.
The same paths on Dagu, OMB or an extension still strip the web-session cookie.
Native app cookies remain intact.

Future OAuth/LDAP providers use Tinyauth's native YAML fields, not a new framework
provider schema. Secret fields can reference `${FYSO_AUTH_<NAME>}` variables from
the existing encrypted secrets file. Small startup glue resolves only that prefix
and writes the native configuration with private permissions. Tinyauth 5.2.0
selects the first applicable configuration loader, so YAML and environment values
must not be assumed to merge. Unknown/missing referenced secrets fail startup.

Enabling an external provider must also add its explicit app allowlists, validate
stable subject/account mapping, callback redirects, logout and group permissions.
Provider availability is not evidence that those integrations have been tested.

## Native application identity limits

Dagu remains in Basic mode on loopback and receives its **technical** credential
from Caddy after human authentication. Its licensed trusted-header SSO is not
enabled. OMB receives its existing native gateway bearer, held server-side.
Neither credential is sent to the browser or replaced with a user's password.

The shared identity therefore authenticates and authorizes **gateway access**.
It does not create separate native Dagu/OMB users, enforce per-user bot histories,
or provide native per-user audit attribution. Passing trusted identity headers
does not imply these products consume them. Real per-user application isolation
requires supported upstream identity integration and separate acceptance.

## Native installation and verification

`mise run web-auth:install` installs the unmodified pinned Tinyauth (D87). On Linux it
downloads the upstream release binary (`tinyauth-amd64`/`tinyauth-arm64`) and checks the
SHA-256 pinned in `mise.toml`. Upstream publishes no macOS binary: the installer app
bundles a universal one built from the pinned source tag (archive checked against
`FYSO_TINYAUTH_SHA256`), and the task copies it into
`${XDG_CACHE_HOME:-~/.cache}/fyso/web-auth/<version>-<source sha256>-darwin/` only when the
bundle's version, source checksum and binary checksum match the project's pins. Without a
matching bundle it builds that source once per machine into the same cache, with the
pinned Go and pnpm (`FYSO_TINYAUTH_GO`, `FYSO_TINYAUTH_PNPM`, installed on demand) and the
upstream lockfiles. Each project copies the cached binary after checking its SHA-256; a
different pin never reuses it. No Docker, custom auth server or Caddy plugin is added.
`mise run up` ensures the binary exists before starting services.

`mise run doctor` checks the native authority and verifies unauthenticated page/API
boundaries, including rejection of technical Basic credentials at the browser
gateway. It does not invent a browser session from a password hash; authenticated
browser checks are separate evidence.

Regression entry point:

```sh
FYSO_TEST_TINYAUTH=<explicit-native-binary> \
FYSO_TEST_CADDY=<explicit-caddy-binary> \
python3 -m unittest discover -s tests -p test_web_auth_http.py -v
```

The suite starts isolated real Caddy/Tinyauth processes and echo upstream fixtures.
It verifies one-session routing, rejected forged identities, technical credential
replacement, cookie stripping, app ACLs, retry protection, logout replay denial,
cross-origin requests and authority failure. Real Dagu/OMB and browser evidence
are reported separately in the [delivery evidence](../artifacts/delivery-evidence/web-auth/README.md).
For the optional Biz feedback case, see its [fixture prerequisites](biz-feedback-delivery.md#isolated-validation).
